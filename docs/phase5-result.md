# Phase 5: release builds (in progress)

Work in the worktree `wt/phase5-release`. Steps as in [PLAN.md](PLAN.md#phase-5-release-builds-for-the-owners-machines).

## Step 1: version (done 2026-11-25)

`build.zig.zon` 0.1.0; [CHANGELOG.md](../CHANGELOG.md); `rweb --version` (stdout) prints version, commit,
build mode and target, Ghostty tag and Rex API revisions. The commit comes from `-Dcommit=` or `git
rev-parse HEAD`, and is `unknown` in an export built without `-Dcommit` (checked). The bridge reports the
version to Rex as its client version.

## Step 2: `zig build dist` (done 2026-11-25)

- Targets: `macos-arm64` (aarch64-macos) and `linux-x86_64` (x86_64-linux-musl, static: runs on any
  distribution; gateway-box is x86-64 too). `ReleaseSafe`, stripped. Built from macOS in about a minute.
- `tools/dist.sh` packs `rweb-<version>-<target>.tar.gz` (binary, README, CHANGELOG,
  THIRD-PARTY-NOTICES) deterministically (sorted members, owner 0, fixed modes and time, `gzip -n`) and
  writes `SHA256SUMS`. BSD tar and GNU tar each have their own branch.
- `THIRD-PARTY-NOTICES.md` is generated by `tools/notices.py` from the licence files of what the binary
  links or serves: Ghostty, simdutf, Highway, Wuffs, uucode (+ Unicode data and Hoehrmann's decoder, whose
  licence files the uucode package omits: stored in `tools/licenses/`, fetched from uucode at the commit
  Ghostty pins, `1fb73433`), Zig's standard library, musl (Linux), xterm.js, wterm. LLVM's libc++,
  libunwind and compiler-rt are named (Apache-2.0 WITH LLVM-exception). Rerun on any pin change.
- No rweb `LICENSE` in the archive: the project's licence is a Phase 6 gate.
- The macOS binary is ad-hoc signed by the linker (`codesign -dv`: `adhoc,linker-signed`) and runs.

## Reproducibility (measured 2026-11-25)

| Build | Result |
| --- | --- |
| Same machine, same folder, fresh export each time | byte-identical archives |
| Same machine, different folder | binaries differ in ~70 bytes: Highway's C++ embeds `__FILE__` of a header under `.zig-cache/o/<hash>/`, and the hash depends on the build folder (Ghostty's build flags, not ours) |
| macOS (Homebrew Zig 0.17.1) vs linux-box (Arch Zig 0.17.1), same folder | binaries differ (16 bytes in size, plus the cache path); archives also differ in tar headers (BSD vs GNU tar) |

So `tools/release.sh [COMMIT]` builds from a `git archive` export at the fixed path
`/tmp/rweb-release/<commit>` with `-Dcommit`, and copies the archives to `zig-out/release/<version>/`.
That is reproducible on one machine with one Zig. Matching across machines would need the same Zig build
everywhere (an official ziglang.org tarball pinned by checksum) and one tar; not done, owner's decision.
The likely cause of the Zig difference (each distribution's Zig linked against its own LLVM) is not
verified.
